# 课 4-4：多 Agent 协作框架与"何时真正优于单 Agent"

> 模块 4：Agent 实践 ｜ 教材：ai-agent-book ch10「多 Agent 协作」前半
> 状态：✅ 讲义已生成（2026-08-14），内容基于本地 clone 教材原文逐节提取

## 教学目标
1. 掌握多 Agent 分类框架的两个设计维度（上下文共享 + 协作拓扑）
2. 掌握核心判据：**是否引入单 Agent 无法获得的新信息**
3. 理解步骤预算与成本账（多 Agent 何时不划算）

## 知识点详解

### 1. 为什么需要多 Agent
- OpenAI 五等级（对话者/思考者/智能体/创新者/组织）中多 Agent 常被类比为通向第五级"组织"的路径
- 核心论点：多 Agent 的意义不止"取长补短"，更根本的是**群体的智能可以高于个体**（人类文明即明证）

### 2. 分类框架（两个设计维度）
**维度一：上下文是否共享**
- 共享上下文：后一个 Agent 继承前一个的完整对话历史与轨迹（换系统提示词与工具集，保留全部记忆）——信息零丢失但上下文快速膨胀
- 不共享上下文：各 Agent 完全独立，无法访问对方思考过程——模块化隔离好但需显式通信
- 三种通信机制（对应 OS 两大范式：共享内存 vs 消息传递）：
  1. **工具调用的参数**（下游 Agent 封装为工具，结构化传参）
  2. **共享文件系统**（读写中间产物 = "共享内存"）
  3. **消息总线**（中转站异步转发）
- Go 名言："不要通过共享内存来通信，而要通过通信来共享内存"

**维度二：协作拓扑**
- 对等协作（少量 Agent 固定拓扑迭代改进）/ 管理者模式（中心化 Manager 调度子 Agent）/ 去中心化模式（无中心控制者，像人类互相沟通）

### 3. 核心判据：新信息增量（必背）
- **唯一核心判据：协作过程是否引入了单个 Agent 在生成时无法获得的新信息**
  - 同模型自我审查、多 Agent 辩论同一文本 → 不引入新信息 → 无效/持平
  - 用测试执行结果、渲染截图、外部工具验证事实做审查 → 引入新信息 → 显著提升
- 例证（书中）：RLEF 用代码执行反馈迭代改进远胜独立多次采样；WebGen-Agent 用多层视觉反馈使 Claude 3.5 Sonnet 26.4%→51.9%
- **该框架解释了"学术研究认为多 Agent 无效、工程实践却有效"的矛盾**：前者多是无新信息的讨论模式，后者含外部反馈环路

### 4. 步骤预算与成本账
- Google《Budget-Aware Tool-Use》发现：单纯增加步骤预算不能保证提升——Agent 缺乏"预算意识"，会浅层搜索后"饱和"；需显式预算感知（前期广探索、后期深挖掘）
- 启示：Manager 应按子任务复杂度**动态分配步骤预算**
- **成本**：多 Agent 并行探索与反复迭代消耗大量 token——收益必须大到能覆盖数倍乃至一个数量级的额外开销，否则调校得当的单 Agent 更划算

## 记忆点
1. 两维度：上下文共享与否 × 拓扑（对等/管理者/去中心化）
2. 三通信机制：工具参数 / 共享文件系统 / 消息总线
3. 核心判据 = 新信息增量；步骤预算需显式；成本账算得过才用多 Agent

## 面试话术
> "多 Agent 不是银弹：先问'协作引入的新信息是什么'——测试结果、渲染截图、独立事实核查才算数，纯讨论不算。这个判据能解释为什么学术上多 Agent 常常无效、工程上却有效。"
