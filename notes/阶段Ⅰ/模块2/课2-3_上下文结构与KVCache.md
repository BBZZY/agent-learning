## 教学目标
1. 掌握上下文的五部分构成与消息的四种角色
2. 理解 ReAct 循环在 API 层面的实现（messages 列表管理）
3. 掌握 KV Cache 的原理与三条黄金实践原则（前缀不动、动态信息追加末尾、用标准格式）

## 知识点详解

### 1. 上下文 = 决定 Agent 能力上限的关键
- 核心论点：**中等模型 + 精心组织的上下文，常胜过顶级模型 + 信息匮乏**
- 类比：天才工程师加入团队却不懂产品架构、技术债务、团队规范，也难以发挥——AI Agent 就是"永远的新员工"
- 上下文质量 = 进入上下文的对环境的观察/描述/配置（不是环境本身）

### 2. 消息的四种角色（API 视角）
| 角色 | 含义 |
|---|---|
| system | 系统提示词：身份、行为规则、约束（对话全程不变，最高优先级） |
| user | 用户消息（可能含 RAG 注入的外部知识） |
| assistant | 模型回复（思考 reasoning + 文本 content + 工具调用 tool_calls） |
| tool | 工具执行结果（靠 tool_call_id 关联） |

- **模型只发调用请求，真正执行工具的是 Agent 框架**——模型决策、框架执行
- 每次 API 调用无状态：所有历史必须完整重发；**Agent 框架的核心工作就是管理 messages 列表**

### 3. 上下文结构：静态前缀 + 轨迹
- 上半部分 = System Prompt + Tool Definitions（全程不变）
- 下半部分 = 对话历史轨迹（不断增长）
- 这个结构是后面所有 KV Cache 优化与压缩技术的基础——"**前面不能动、后面可以压缩**"

### 4. KV Cache 原理
- 模型每生成一个 token 都要"回头看"前文所有 token 的中间结果（K、V 向量）
- KV Cache 把前文中间结果缓存，下一轮只算新增部分。**前提：要复用的前缀保持不变**
- 两个层级：**KV Cache**（单次推理内的缓存）vs **Prompt Cache**（跨请求前缀缓存，命中后读取成本约 1/10，Anthropic/DeepSeek/GPT-5 均有，计费细节以官方文档为准）
- 无缓存时 prefill 注意力计算量随上下文长度平方级增长——Agent 几十轮工具调用任务必须缓存

### 5. 三条黄金实践原则（必背）
1. **系统提示词和工具定义一旦确定就不要改**（多一个空格都可能变 token 序列；改动越靠前影响越大）
2. **动态信息永远追加到末尾**（时间戳、用户状态作为新消息追加，不修改已有 system）
3. **使用标准 API 格式，不要自行拼接消息**（"USER: ..." 纯文本流偏离训练格式，模型需额外消耗注意力推断角色边界）

### 6. 反模式案例（书中实验 2-3 五个错误模式）
- 动态系统提示词（每请求插 `Current time: {{now}}`）→ 首 token 延迟 0.5s→3-5s、月度账单几乎翻倍
- 动态用户配置、工具定义动态排序 → 缓存失效
- **滑动窗口**：破坏前缀一致性 + 丢失关键工具结果（Agent 忘记已获得的结果→死循环）
- 文本格式化拼接 → 偏离训练格式（最破坏性之一）

### 7. 缓存作为架构约束（生产级视角）
- 提示词结构由缓存边界决定：缓存边界标记前的内容可跨用户全局缓存，边界后是会话特定信息
- N 个运行时条件放边界前 = 2^N 种缓存键组合 → 动态元素必须放边界后
- 子 Agent 必须与父 Agent 字节级对齐（提示词/工具定义/模型配置逐字节匹配才能命中缓存）

## 记忆点
1. 上下文 = 静态前缀 + 轨迹；四个角色 + tools 字段
2. KV Cache 前提 = 前缀字节级不变；Prompt Cache = 跨请求缓存（读取约 1/10 成本）
3. 三原则：前缀不动 / 动态追加末尾 / 标准 API 格式

## 面试话术
> "上下文工程的第一课是 KV Cache：前缀一动缓存全废，动态信息只能追加到末尾。这一条设计约束决定了生产级 Agent 的提示词结构、状态注入方式甚至子 Agent 的上下文对齐。"
